# 第六章 · 意图识别与对话管理 — 开发记录

## 阶段：Brainstorm 定稿（2026-11-18）

### 用户这一步发的关键原话

- 总目标：「我要用 Superpowers 模式把客服系统里占位的分流器做成正式版，这是 Workflow 里最关键的节点。」
- 七条需求（原话要点）：
  - 「指代消解：用 LLM 结合对话历史，把『它能退吗』这种带指代的话补全成一句不依赖上下文也能看懂的完整问题；问题本身已完整、指代已明确的，原样透传，不强行改写。」
  - 「Query 改写：口语模糊问法归一成标准问法，和指代消解一并处理。」
  - 「Query 扩写：把一句问题泛化成多条侧重点不同的检索查询（强制 JSON 输出，字段就 queries 一个数组），几条一起检索再去重合并；只对退款退货、售后这类高频、容错低的核心场景做；扩写放检索侧现查现用，库里知识只留一份。」
  - 「意图识别用 LLM prompt 路线，不训分类模型：七类枚举成选择题、强制 JSON `{intent, confidence}`、边界 few-shot、留『其他』兜底。」
  - 「分流精化：退款退货和售后走一条确定性子流程——先拿订单数据、再做 Query 扩写并强制检索政策条款，最后只把『这一单能不能退』交给主力 Agent 判断。」
  - 「槽位处理：缺订单号不让模型猜，执行阶段弹订单选择器让用户点选回填；退款原因不追问，用户提交退款单时从固定类目里自选；需求澄清留在主力 Agent 里做。」
  - 「前端配套：订单选择器做成聊天流里可点选的订单卡片；退款单是简单表单，退款原因固定下拉。」
- 技术栈：「无新增组件，延用现有聊天上游；意图识别默认配够格的大模型先把准确率做上去，成本吃紧时再走降级路。」
- 章节不做：「微调小模型 / BERT 做意图分类」「跨会话记忆」。
- 工作方式：「全程走 Superpowers 流程，技能自动触发；纯 Prompt、数据类任务把 TDD 换成标注样例或评估集；前端部分用 Vibe Coding，不套 brainstorm、TDD、code review。」「dev-notes/ch06.md 每个阶段追记，不许收尾时一次性补记。」「涉及库/框架/API 先用 Context7 查最新文档。」「技术选型定死，走不通停下来问。」
- 订单数据源选择：「a」——固定演示订单 1001/1002/1003，不建 orders 表。
- 参考 spec：用户贴出 ch06 参考 spec，并注明「这是参考的spec文档」。
- 「其他」意图冲突裁决：「b」——其他和闲聊一起归 `fallback_script`，用固定文案，不交给主力 Agent。
- 售后 prompt 冲突裁决：「a」——一条通用售后判定 prompt，退款/退货判能不能退，保修/维修/补发走政策说明。
- Spec 定稿：「可以」。

### 我拒绝或纠偏了什么

- **拒绝「其他 → main_agent」**：我推荐过 A（其他交主力 Agent 澄清），用户明确选 B（其他 → `fallback_script` 固定文案）。这覆盖了最初「需求澄清留在主力 Agent」的口径；spec §5.5 与 §7.4 已按 B 写，dev-notes 记录此变更。
- **拒绝把售后强行判成退款**：参考 spec 只写了一个退款资格 prompt；用户选 A，改成一条通用售后判定 prompt，保修/维修/补发不出退款表单。
- **拒绝用原始历史扫描订单号**：会把旧订单硬塞给新问题，违反反目标 #1；改为只认本轮 `resolved_query`，拿不到就弹选择器。
- **拒绝目录外订单号进入退款流程**：1004/年份数字不再调 `query_order`，避免退款 prompt 缺 `signed_at`、前端表单提交时才被拒。
- **拒绝让 pending interrupt 卡死线程**：后端检测 pending 时重发订单卡片，无 pending 的 resume 返回 409，不把恢复逻辑全推给前端。
- **拒绝让选择器回填对后续轮次不可见**：改为写 `SystemMessage` 进 checkpoint，MySQL 另写审计；否则下一轮「这个能退吗」只能靠 assistant 答案重复订单号。
- **不照抄参考 spec 的双字段指代输出**：按参考 D5 收敛为单字段 `resolved_query`，放弃我先前 3A 的 `standalone_query/normalized_query` 方案；日志同时打 original/resolved，验收仍能看到补全。
- **不照抄参考 spec 的「退款表单不落库」**：按参考 D2 改为落 `tickets`，`ticket_type='退款'`；需要 SQL 枚举迁移。
- **不整体重命名节点**：保留 `confidence_gate` / `record_log` 原名（参考叫 `confidence_check` / `log`），只改路由键和父图 `agent→main_agent`，避免无意义 churn。
- **拒绝嵌套 `refund_flow` 子图、两轮重入、跨 query RRF**：分别因为流式/中断适配成本、重复分流/检索、闸门分数语义不一致。

### 我的关键产出

- 新增 `tests/test_interrupt_smoke.py`，用最小 `StateGraph` + `InMemorySaver` 钉死 langgraph 1.2.20 实测行为：
  - `graph.stream({}, config, stream_mode="custom")` 跑到 `interrupt(...)` 会停在节点中间，**不**产生 custom 帧；中断信息从 `graph.get_state(config).interrupts[0].value` 读取，实测值为 `{"kind": "select_order", "orders": ["1001"]}`。
  - `graph.stream(Command(resume="1001"), config, ...)` 从同一 thread 续跑，`get_state(config).values["selected"] == "1001"`。
  - 被中断节点**从头重跑**：`calls == ["pre", "pre", "post"]`，即 resume 前副作用（`pre` 前的逻辑）会再执行一次，写代码时不能把不可重入副作用放在 `interrupt` 之前。
- 测试结果：`.venv/Scripts/python.exe -m pytest tests/test_interrupt_smoke.py -q` → `1 passed in 0.28s`。
