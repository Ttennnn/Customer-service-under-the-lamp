# 第七章 · 会话上下文管理 — 开发记录

## 阶段：Brainstorm 定稿（2026-11-18）

### 用户这一步发的关键原话

- 总目标：「我要用 Superpowers 模式让客服在一通会话里记得住前面聊过什么，把第一版的简单裁剪升级成正经的上下文管理。只管当前会话，不跨会话、不存用户画像。」
- 三层结构：「最近的留原文，一个字都不压；中间一层按规则截短，用户原话不动、客服答复只留开头几十个字、大块工具结果换成一行标识；最远的异步压成一段段梗概。两个锚点划边界，summary_upto_msg_id 标出摘要覆盖到哪条，layer1_from_msg_id 标出层 1 从哪条起，降级只挪这两个 id、不搬数据。梗概单开一张会话摘要表，不塞进逐条消息里。」
- 摘要异步：「中间那层攒到超预算就在后台起一次摘要任务，把这一批压成新的一段追加进摘要表，边界追到层 1 起点，全程不阻塞用户当前这轮回复。梗概一段段攒、压完不回头重写，旧梗概只作背景给模型看、不参与合并，免得同一个事实被反复有损压缩。触发看用量不数条数，工具结果压根不落消息表，数条数看不见它涨。摘要提示词只提炼事实与诉求（问过哪款商品、报过的订单号手机号、明确诉求、还没解决的问题），对话里没出现的内容一个字不许编，寒暄闲聊不留，长度控制在几十到一两百字。」
- 拼装顺序：「system 人设、红线和工具定义打头，这一段每轮都一样；接中间那层截短过的对话，再接最近几轮原文，然后是用户当前这句话；早期梗概和检索证据合成一条挂在用户这句之后。梗概不许单独占一条 system，上游模板会把所有 system 上提合并渲染，工具定义被挤到可变内容之后，前缀缓存整段作废。」
- 预算：「token 预算从模型窗口倒推，不写死成常量：扣掉系统提示、检索证据、注入梗概、输出预留和安全余量这些固定开销，再扣掉当前这一轮 ReAct 的瞬时峰值，剩下的才归历史；历史预算取『想留住的轮数 × 每轮稳态占用』和『窗口实际匀得出来的』两个数里小的那个，层 1 拿七成、层 2 拿三成。启动时自检一遍，连一轮都装不下就报警。中文按字数折 token 的口径要和预算一起校准，只改一个净效果是反的。」
- 双轨：「对话历史落在 conversations 和 messages 两张表里，会话上下文随 LangGraph 的 State 一路贯穿：State 的 messages 字段挂 add_messages reducer，各节点只管吐新消息、框架自动按顺序并入；State 里的完整历史靠 checkpoint 落盘留着，调模型前另外整理一份裁过、带摘要的精简版递进去，完整历史和精简版各走各的、互不影响。」
- 可观测：「每轮调模型前，把实际发出的上下文原样打进 log/app.log——主力 Agent 打 model_ctx（摘要全文 + 滑窗逐条消息 + 窗口条数 + tokens 估算），指代消解/意图识别共用的历史打 history_ctx（摘要行 + 滑窗，每轮必打，不进 Agent 的闲聊兜底轮也看得到）；后台摘要任务的触发/开始/完成/跳过/失败全留痕，带覆盖边界和耗时。」
- 前端：「聊天页加会话侧栏，列出该用户全部会话（新在前、首问预览、已摘要标记），点击切换并回载历史原文继续聊；『新对话』只是开新会话，旧会话仍在侧栏可切回；后端配两个只读接口（GET /api/conversations、GET /api/conversations/{id}/messages），侧栏加载失败静默降级不影响聊天。」
- 表结构：用户给出两段 DDL，要求 `sql/ch07-ddl.sql`（summary、summary_upto_msg_id）和 `sql/ch07-layers.sql`（layer1_from_msg_id、conversation_summaries）都要 apply；`conversation_summaries` 一段一行、只追加，`(conversation_id, seq)` 唯一。
- 演示配置：「MODEL_CONTEXT_WINDOW=18000 MAX_OUTPUT_TOKENS=2000 MAX_USER_INPUT_TOKENS=2000 MAX_AGENT_STEPS=3 TOOL_RESULT_MAX_TOKENS=1200 RERANK_TOP_K=5。这组算出来滑窗 5650、层 1 预算 3954、层 2 预算 1695。」
- 预算确认：「对的」。
- 方案选择：「a」（runtime 预处理窗口）。
- 设计评审：「可以」。

### 我的关键产出

- 设计文档：`docs/superpowers/specs/2026-11-18-ecommerce-cs-ch07-context-management-design.md`。
- 分支：`feature/ch07-context-management`，从 `feature/ch06-dispatcher` 拉出。
- Context7 已核实：
  - `add_messages` 按消息 id 追踪，同 id 更新、新 id 追加；`db-{msg_id}` 唯一。
  - `graph.get_state(config)` 必须给 `thread_id`；新输入不会清空 thread，要隔离会话必须换 `thread_id`，所以用 `conv:{cid}`。
  - `Command(resume=...)` 用同一 thread 恢复，被中断节点从头重跑。
  - `trim_messages(strategy="last", token_counter=..., max_tokens=..., start_on="human")` 调模型前裁剪、不改 State，只作 L1 兜底。
- 预算公式反推并与用户确认：
  `history = window - (system 1200 + rerank_top_k*250 + summary 500 + output 2000 + 10% safety) - (user_input 2000 + max_steps*tool_result_max)`。
  演示配置：18000 - 6750 - 5600 = 5650；L1=3955、L2=1695。只改窗口、其余默认：18000 - 8000 - 14000 = -4000，滑窗归零并报「上下文预算不足」。
- 独立 builder 预审（读设计与现有 ch06 代码）提出 7 个会改变计划的问题，全部在 spec 内裁决：
  1. 旧 `MAX_CONTEXT_TOKENS` / `AGENT_TOKEN_BUDGET` 会二次裁剪/提前耗尽 → ch07 退役，只保留给旧链路。
  2. 一张图还是两张图、用哪个 checkpoint DB → `/ch07/chat` 与 `/ch06/chat` 共用一张图，统一 `CH07_CHECKPOINT_DB`，旧 ch06 thread 不迁移。
  3. 退款/工单归属哪个会话 → `RefundRequest` / `TicketRequest` 增加可选 `conversation_id`。
  4. 消息接口是否按用户校验 → 可选 `user_id`，不匹配 404。
  5. 旧会话第二轮丢历史 → 每轮把 State 之前的 MySQL 行补合并。
  6. `log/app.log` 没有日志落点 → 新增 `app/logging_config.py`。
  7. `[订单选择]` 审计行和订单选择器 → 不进前端历史，摘要按系统事实行处理，订单选择器改 HumanMessage。

### 我拒绝或纠偏了什么

- **拒绝照搬参考 spec 的旧方案**：参考 spec 写的是「双层 + 满 30 条消息触发 + 滚动重写 summary」；用户这一版明确改成「三层 + 按 L2 token 用量触发 + 分段追加、不回炉重写」。参考 spec 只保留结构参考。
- **拒绝 `asyncio.create_task`**：当前 SSE 端点是同步生成器、跑在线程池，没有事件循环；改用模块级线程池 + 每会话在飞标记。
- **拒绝每轮从 MySQL 重建整个窗口（方案 B）**：tool 结果不落库，L1 原始工具结果和 L2 用量都看不见，违背「触发看用量」。选 runtime 预处理 State（方案 A）。
- **拒绝每个节点各自切窗（方案 C）**：coref/agent/日志三处重复，降级边界没有单一入口。
- **拒绝把摘要/证据/订单数据留在 system**：全部搬到用户这句之后的「本轮材料」，system 每轮恒定；订单选择器从 SystemMessage 改成带标签的 HumanMessage，避免上游模板上提。
- **拒绝保留旧预算 gate**：`MAX_CONTEXT_TOKENS` 二次裁剪和 `AGENT_TOKEN_BUDGET` 提前耗尽会让窗口预算形同虚设；ch07 退役，只留 `MAX_AGENT_STEPS` 控步数。
- **纠偏 `[订单选择]` 的语义**：它是审计行，不是用户原话；前端历史过滤，摘要按「用户选择了订单 N」的系统事实行处理，避免假用户气泡和摘要误记。

### 翻车与返工

- 无代码翻车（仍在设计阶段）。
- 一次数字口径未对齐：用户写 L1=3954，按 70% 向下取整实际是 3955（L1+L2=5650）；已在设计文档注明，实现按 3955/1695，日志同时打印 5650。
- 一次设计补洞：builder 预审发现旧 `MAX_CONTEXT_TOKENS` / `AGENT_TOKEN_BUDGET` 会绕过新预算、旧会话第二轮会丢 MySQL 历史、退款/工单会归错会话、日志没有文件落点；均已回写设计文档。
