# 第五章 · Agent 工作流 — 开发记录

## 阶段：Brainstorm 定稿（2026-11-17）

### 用户这一步发的关键原话

- 总目标：「我要用 Superpowers 模式把客服系统升级成生产级架构：Workflow 确定性编排做骨架，主力 Agent 作为骨架里的核心节点。」
- 祛魅热身：「先不用框架，手写一遍最裸的 Agent 循环（调 LLM，有工具调用就执行并把结果喂回去，没有就收敛出答案），看清它就是个带工具的循环，再用 LangGraph 重构。」
- 图骨架：「指代消解、意图识别、按意图分流、知识检索、置信度闸、主力 Agent、日志记录。」
- 分流规则：「知识类（商品咨询、退款退货）强制先 RAG，检索完先过置信度闸，证据够才把检索结果连同问题交给主力 Agent；退款退货先检索政策再交给 Agent，Agent 仍可自己调订单工具。业务数据类（物流、订单、售后）不预检索，直接进 Agent。投诉不进 Agent，回安抚话术，把『转人工』『建工单』两个选项交用户自己选，不后端自动执行。闲聊直接返回固定话术，不花模型调用。」
- Agent 要求：「ReAct 循环，简单问题一次工具调用收敛，复杂问题多走几步，缺信息追问；有停止条件和 token 消耗控制；工具复用第 2 章，不新写业务工具。」
- 状态要求：「会话状态用 LangGraph 的 State 一路贯穿，持久化用自带的 checkpointer。」
- 本章最简项：「指代消解先原样透传；意图识别用简单 prompt 判成物流、订单、商品咨询、退款退货、售后、投诉、闲聊七类，输出 JSON。」
- 闸门要求：「卡在知识类检索之后、进 Agent 之前；Agent 答复流式吐给用户，答完再判就晚了；证据弱就回兜底话术、不进 Agent，并把问题记下来留给数据飞轮；业务数据类不走这道闸。」
- 按钮要求：「转人工、建工单是两件事，分开做，都交用户在前端自选、不后端自动执行；点『转人工』前端展示『已转接人工客服』再蹦『您好，我是客服小猫，请问有什么可以帮您的』；点『建工单』才调第 2 章工单工具写 tickets 表；两个按钮互不绑定，都不点继续正常对话。」
- 前端要求：「原生 HTML + CSS + JavaScript 聊天页，只在上面加两个按钮 + 确认交互。」
- 过程要求：「全程走 Superpowers；纯 Prompt/数据任务把 TDD 换成标注样例或评估集验证；dev-notes/ch05.md 每个阶段追记，记四样，不许收尾一次性补；涉及库/API 先用 Context7 查最新文档；技术选型定死，走不通停下来问。」
- 三个定夺：
  - 前端落点：「新开 /ch05 原生页（推荐）」。
  - 工单语义：「改工具，只写 tickets（推荐）」。
  - Checkpointer：「加 SQLite checkpointer（推荐）」。
- Agent 形态：「B. Agent 子图（推荐）」。
- 设计定稿：「可以」。

### 我的关键产出

- 设计文档：`docs/superpowers/specs/2026-11-17-ecommerce-cs-ch05-agent-workflow-design.md`。
- Context7 已核实：
  - LangGraph `StateGraph` + `compile(checkpointer=...)`；`thread_id` 区分会话；父图 checkpointer 自动传播给子图。
  - 子图 custom 流在 langgraph 1.2.20 下必须 `subgraphs=True` 才收得到；本章只消费 `custom`，最终状态用 `get_state`。
  - `get_stream_writer` 可在节点内发自定义帧；`stream_mode="custom"` 接收。
  - LangChain 流式工具调用用 `gathered = gathered + chunk` 累加 `AIMessageChunk`，结束后取 `tool_calls`。
  - `langgraph-checkpoint-sqlite` 3.1.3 的 `SqliteSaver(sqlite3.connect(path, check_same_thread=False))`；首次 `setup()`；本地/单机持久化，生产应换 Postgres。
- 方案选择：
  - 父图骨架 + Agent 嵌套 ReAct 子图（`agent ↔ tools` + 条件边 + `finalize`）。
  - 七类意图硬编码映射四出口；知识类强制检索 + Top-1 重排分闸门；业务类直接 Agent；投诉/闲聊固定话术。
  - Agent 工具只绑定 `query_order` / `query_product` / `query_logistics` + 控制工具 `suggest_handoff`；`query_faq`、`create_ticket` 不绑定。
  - `/ch05` 原生页 + `/ch05/chat` / `/ch05/tickets`；旧 React `/chat` 不动。
  - 修改 `create_ticket`：只写 `tickets`，不再改 `conversation.status`；`/ch05/tickets` 关闭自动重试，防止重复建单。
  - `thread_id = f"user:{session_id}"`，不依赖 MySQL 自增 id。
- Builder 预审（独立 subagent，读设计与现有代码）提出 8 个会改变计划的问题，全部在 spec 内裁决：
  1. 子图 custom 帧默认收不到 → `subgraphs=True`。
  2. rerank 失败时 RRF 分数不能过 0.3 闸 → 新增 `rerank_failed` 闸门原因，保守兜底、不落池。
  3. `suggest_handoff` 契约不清 → 固定 schema、union 去重、非法选项回错误 ToolMessage。
  4. 固定话术节点没写回 messages → 所有终态节点发 token 帧并追加 `AIMessage`。
  5. graph/checkpointer 构建与测试注入 → lifespan 构建 + `build_graph(...)` 注入 + dependency_overrides。
  6. `/ch05/tickets` 成败判定与重复建单 → `retries=0` + 工单号正则 + 失败 502。
  7. 知识轮工具事实的引用规则 → 知识事实必须 `[n]`，工具事实不得带 `[n]`。
  8. MySQL 重建后 thread_id 复用 → 改用 `user:{session_id}`。

### 我拒绝或纠偏了什么

- **拒绝让 Agent 自动建工单**：`create_ticket` 不绑定给 Agent；新增 `suggest_handoff` 只记录选项、不执行动作，保证「不后端自动执行」。同时修改 ch02 工具，去掉「建工单顺手改会话状态」的副作用，保证转人工与建工单互不绑定。
- **拒绝 Agent 重新检索绕过闸门**：Agent 不绑定 `query_faq`；知识类必须走父图的强制检索 + 置信度闸。
- **拒绝把 rerank 失败当弱证据落低置信度池**：RRF 分数与重排分不可比，重排失败属于基础设施故障，保守兜底并只记日志。
- **拒绝在 import 时构建 graph**：会把真实 checkpointer 和真实模型带进测试；改为 lifespan + 可注入的 `build_graph`。
- **拒绝用 conversation.id 做 thread_id**：MySQL 重建后自增 id 可能复用，导致 checkpoint 串档；改用 `user:{session_id}`。
- **拒绝在闸门失败时给按钮**：避免和投诉/Agent 建议的按钮语义混淆；闸门失败只回兜底话术。
- **纠偏「闲聊不花模型调用」的口径**：意图分类本身需要一次模型调用；「不花模型调用」指闲聊回复不调生成模型。已在设计文档中写明，避免验收时口径不一致。

### 翻车与返工

- 无代码翻车（仍在设计阶段）。
- 一次设计返工：初稿写的是 `stream_mode=["custom","updates"]` 且未开 `subgraphs=True`，Builder 预审指出在 langgraph 1.2.20 下会丢掉 Agent 子图的所有 token/tool 帧；已改为 `stream_mode="custom", subgraphs=True` + `get_state` 取终态。
- 一次设计补充：初稿只让 Agent 路径写回 `messages`，投诉/闲聊/闸失败/finalize 只设 `answer`，会导致下一轮 history 连续 HumanMessage；已补「所有终态节点发 token 帧并追加 AIMessage」。
