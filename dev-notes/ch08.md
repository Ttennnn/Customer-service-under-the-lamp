# 第八章 · 工具系统 — 开发记录

## 阶段：Brainstorm（进行中，2026-11-19）

### 用户这一步发的关键原话

- 总目标：「我要用 Superpowers 模式把客服系统的工具层从几个写死的内置工具，升级成即插即用的工具系统。」
- 六项功能：工具注册中心（内置启动登记 + MCP 动态发现 + 新工具免改核心代码、免重启）、JSON Schema 参数校验（错误包成工具结果回灌）、权限控制（只读/写两类，写操作只有 `create_ticket`，必须客户明确要求且前端确认，MCP 工具声明不可信）、统一执行引擎（超时/重试/错误分诊/结果格式化，写操作不自动重试）、`tool_audit_logs` 审计（被拒/被拦也落，不挂外键，审计失败不拦执行）、两个业务 MCP Server（物流、售后，独立进程，Streamable HTTP；内置 `query_logistics` 下线）+ 建工单 interrupt 确认流（前端预览卡片，确认/取消两条路）。
- 技术栈定死：MCP Server 用官方 Python SDK + Streamable HTTP；MCP Client 用 `langchain-mcp-adapters` 的 `MultiServerMCPClient`。
- 本章不做 Skill 机制；不接仓储等更多外部系统。
- 验收：1）新工具只注册即可用；2）两个 MCP Server 独立进程可查；3）MCP Server 热加工具只重启该 Server，客服系统不重启可用；4）建工单缺信息先追问，预览卡确认后落 tickets 并回工单号；5）取消则权限拒绝审计；6）读超时有重试/兜底且审计齐全，写超时不自动重试。
- 过程要求：全程 Superpowers；纯 Prompt/数据任务用标注样例或评估集替代 TDD；前端预览卡片用 Vibe Coding，不套 brainstorm/TDD/code review；`dev-notes/ch08.md` 每阶段追记四样；库/API 先查 Context7；选型矛盾先问；完结交付演示命令、测试结果、dev-notes 路径。

### 我的关键产出（进行中）

- 已读现有实现：`app/tools/{registry,executor,business,ticket,faq}.py`、`app/agent/{subgraph,graph,service,tools}.py`、`app/api/{ch05,ch06,ch07}.py`、`app/static/ch07.html`、`app/prompts/customer_service.py`、`app/models/ticket.py`。
- 现状确认：工具注册表是静态 `ALL_TOOLS` 列表；执行器统一走 `execute_tool`，已有超时/重试/参数校验雏形；`create_ticket` 目前只由 `/ch05/tickets`、`/ch06|07/refunds` 直接调用，Agent 明确不绑定；订单选择器已用 `interrupt` + `/ch0x/chat/resume`。

- 两个待设计化解的风险：
  - LangGraph 节点在 interrupt resume 时会从节点开头重跑；若把确认中断塞进现有 `tools` 节点，同批已执行的只读调用会重复执行，写操作更危险。
  - `langchain-mcp-adapters` 返回的 MCP 工具是异步工具，而当前执行引擎是同步线程模型，需要一层可靠的事件循环桥接。

### 设计进展

- 用户选择插件方案 A：`app/tools/plugins/` 丢文件即自动登记，不改核心注册表。
- 用户选择方案 1：统一 ToolSpec 注册中心 + 单一执行管道 + 独立 `ticket_confirm` 节点。
- 设计文档初稿：`docs/superpowers/specs/2026-11-19-ecommerce-cs-ch08-tool-system-design.md`。
- 已定关键机制：
  - MCP 每轮现查、失败沿用旧快照；内置优先，MCP 不能遮蔽内置工具名。
  - `create_ticket` 未确认只进 `pending_ticket`，不落库不落审计；确认才执行，取消落「权限拒绝」。
  - `interrupt` 只放独立 `ticket_confirm` 节点，避免 resume 重跑 `tools` 节点。
  - 写操作 0 重试，读操作只对暂时性故障重试 1 次；空结果不重试、审计记「成功」。
  - MCP 工具在本侧一律只读，忽略 Server 声明。
  - legacy `/chat` 只绑定只读工具，不提供建单死路；同时失去内置物流（物流由 MCP 接管）。
- 已发独立 builder 预审，等待问题回来。

### Builder 预审（独立 subagent，2026-11-19）

- 提出 7 个会改变计划的问题 + 1 个次要问题。逐项裁决：
  1. **审计 DDL 缺失**：用户原始消息已给完整 DDL，已原样补进设计文档附录 A，并写明 ORM 映射（`BIGINT UNSIGNED`、中文 ENUM、JSON 字段、无外键）。
  2. **ch05/ch06 如何过确认闸**：这两个 HTTP 端点是用户点按钮/交表单触发的可信服务端动作，调用引擎时显式 `confirmed=True`，审计 `tool_call_id=NULL`；「只有 `ticket_confirm` 能确认」只约束模型发起的调用。`/ch06/refunds` 保持 `retries=0` + 502。
  3. **业务错误/空结果契约**：给 ToolSpec 加 `classify` 分类器；默认空串→empty、其余→ok；`query_faq` 用 `MISS_TEXT/ERROR_TEXT` 判空/错且原文不包装；`create_ticket` 用 `T\\d{11}` 判成功；MCP 用 `found:false` 判空。
  4. **快照跨 resume**：快照不塞 checkpoint；一次 `graph.stream` 一份，resume 重新取。State 只存 `pending_ticket` 参数与预览。
  5. **MCP_ENABLED 默认**：代码默认 `False`，演示 `.env` 打开；测试默认零网络。故意不设 true，避免 663 个测试每轮等 2 秒发现超时。
  6. **legacy `/chat` 绑定**：只绑 `query_order/query_product/query_faq`；不绑建单、控制工具、MCP。
  7. **同批多余 `create_ticket`**：算最终调用，走 `deny_validation` 落「校验拦下」，不是「权限拒绝」。
  8. **回复漏工单号**：不只靠 prompt；`ticket_confirm` 写 `created_ticket_no`，服务层落库前确定性追加「工单已创建，工单号：…」。
- 结论：无「只能用户拍板」的遗留问题；设计文档已按上述裁决补全。

### 我拒绝或纠偏了什么

- 拒绝方案 3（内置工具也包 MCP）：多一次 HTTP、确认流更难传，不划算。
- 拒绝方案 2（原地增强 BaseTool）：权限/审计/重试会散落三处。
- 纠正「查询落空算失败」的口径：执行本身成功，审计记「成功」，只是结果为空且不重试。
- 纠正「审计必须完整」的边界：`confirmation_required` 阶段不落审计，等确认/取消时落最终结局；否则每次预览都会留一条无法归类的中间记录。
- 纠正「MCP_ENABLED 默认 true」的想法：会让现有测试每轮等网络超时，改为默认 false、演示配置打开。

### 翻车与返工

- 设计初稿漏写 DDL 与错误分类契约，Builder 预审指出后补全；无代码翻车。
